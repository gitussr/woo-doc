Debugging

How to diagnose unexpected WooCommerce behavior methodically — logging, the System Status report, plugin-conflict isolation, reading the calculation pipeline, and common failure signatures with their causes.

P1 · Core DevelopmentAudienceAll levelsStatusDraft · Step 1 foundationApplies toWordPress 7.1 · WooCommerce 11.0.1

WooCommerce failures rarely have one cause. A methodical order — check the log, check the environment, isolate the conflict, then read the relevant pipeline — finds the answer faster than guessing at a hook.

Logging

wc_get_logger() returns a shared PSR-3-style logger (emergency down to debug). Core and most extensions write through it rather than raw error_log():

Where does this come from?
What am I looking at?
A log entry under WooCommerce → Status → Logs.
Where does it come from?
Written by WC_Log_Handler_File, the default handler — one file per source per day, under wp-content/uploads/wc-logs/.
What controls it?
The source key you pass when logging; the storage location is filterable via woocommerce_log_directory, and the handler itself via woocommerce_register_log_handlers.
What can I safely modify?
Reading logs from the admin **Logs** viewer, or downloading the file directly if you have server access.
What should I avoid?
Logging full request payloads or payment details — a log file is not a secure place for card numbers, tokens, or full customer PII. See Security.

WC_Log_Handler_File rotates a source's log file once it passes 5 MB: the current file is renumbered .0, existing numbered files shift up, and the oldest (.9) is deleted — up to 10 historical files plus the current one. Rotation is size-based, not scheduled; nothing deletes old logs by age automatically (WC_Log_Handler_File::delete_logs_before_timestamp() exists for that, but has to be called explicitly, e.g. from a cron task).

Hook tracing

Tracing which hooks actually fire (and in what order) on a given request is covered in depth on Hooks — Debugging which hooks fire: the all hook trick, reading wc-template-hooks.php, and the Query Monitor plugin, which lists every hook fired on a request with its registered callbacks and file locations. Reach for that page once logging and the status report have ruled out an environment problem.

Plugin-conflict isolation

WooCommerce sits between WordPress core, the theme, and every other plugin — most "WooCommerce is doing something weird" reports are actually a third-party callback on a WooCommerce hook.

A "Troubleshooting" / "Health Check" style plugin that lets you see the site with plugins disabled while other visitors still see the live site is the safe way to run this bisection in production.

Reading the calculation pipeline

"The cart/order total is wrong" is common enough to warrant its own entry point: the pipeline is WC_Cart_Totals, invoked from WC_Cart::calculate_totals() on the woocommerce_before_calculate_totals → calculate → woocommerce_after_calculate_totals sequence. A breakpoint or temporary log line at the start and end of that method, dumping cart contents and fees, isolates whether a plugin changed an item's price (woocommerce_before_calculate_totals) or whether the discrepancy is in tax/shipping/coupon math WooCommerce computed itself.
