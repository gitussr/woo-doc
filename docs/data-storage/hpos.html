HPOS (High-Performance Order Storage)

How order storage works under HPOS — the four order tables and what each holds, the three storage modes and the sync between them, the migration process, and how to write code that is correct in both legacy and HPOS stores.

P1 · Core DevelopmentAudienceIntermediate → AdvancedStatusDraft · Step 1 foundationApplies toWordPress 7.1 · WooCommerce 11.0.1

High-Performance Order Storage replaces "an order is a post" with "an order is rows in tables shaped for orders." It has been the default for new WooCommerce installs since version 8.2; stores created earlier keep legacy storage until a merchant migrates. Either way, the WC_Order API is identical — this page is about what changes underneath it, and what a plugin author must do to stay correct across both.

Why HPOS exists

!What legacy storage cost

An order as a shop_order post meant every field — status, totals, addresses, payment details — was a separate row in wp_postmeta, an unindexed-by-value table shared with every other post type on the site. High-volume stores felt this as slow order queries, lock contention during checkout, and a wp_postmeta table that dwarfed everything else in the database.

HPOS gives orders their own tables with real, indexed columns — the same "stop abusing postmeta" move the product meta lookup table made for products years earlier, applied to the entire order record.

The four tables

woocommerce_order_items and woocommerce_order_itemmeta (the line items, shipping, fees, coupons, tax) are not part of HPOS — they had their own dedicated tables long before HPOS existed, and HPOS did not need to touch them. Only the order record moved.

Three storage modes

Compatibility mode exists so a store — and every plugin it runs — can be verified against both storages before HPOS becomes authoritative. It costs a write penalty (every order write happens twice) in exchange for a safe rollback.

Migration

Switching an existing store from legacy to HPOS is a background job, not a flag flip:

Migration and ongoing sync are driven internally by Automattic\WooCommerce\Internal\DataStores\Orders\DataSynchronizer (batched via Action Scheduler) and PostsToOrdersMigrationController. The same operations are exposed as WP-CLI commands through CLIRunner, under the wp wc hpos namespace (the older wp wc cot namespace still works but is deprecated): wp wc hpos sync migrates the currently-authoritative store to the other one, and wp wc hpos backfill does the same with per-order / per-field control — the practical choice for a large store where the background batches are too slow.

Legacy wp_posts / wp_postmeta rows are not deleted automatically once HPOS becomes authoritative — migration only copies data forward. Deleting them is a separate, explicit step: wp wc hpos cleanup removes the legacy postmeta (and post rows) for orders already migrated, but even then it keeps a lightweight placeholder post (shop_order_placehold) per order so the store can still be switched back to legacy storage without re-migrating.

✓Recommended extension point

On a store with a non-trivial order history, run the migration during low traffic and watch WooCommerce → Status → Scheduled Actions for the batch jobs — do not force it to complete synchronously.

Writing code that works in both modes

Decision guide

If reading or writing an order

wc_get_order( $id ) / wc_get_orders( $args ) and the WC_Order getters/setters. This is storage-agnostic by design — the same call works whichever mode is authoritative.

If querying orders in bulk (a report, an export)

wc_get_orders() with its query args, not WP_Query and not a hand-written join against wp_posts. Under HPOS, WP_Query for orders returns nothing.

If you must run raw SQL for something CRUD cannot express

Detect the active mode first (Automattic\WooCommerce\Utilities\OrderUtil::custom_orders_table_usage_is_enabled()) and branch — query wc_orders or wp_posts accordingly. Treat this as a last resort, and re-check it against every WooCommerce update.

If you are shipping a plugin that touches orders at all

Declare compatibility explicitly — see Architecture → bootstrap: FeaturesUtil::declare_compatibility( 'custom_order_tables', __FILE__, true ) on before_woocommerce_init, after auditing for direct table/postmeta access.

✕Dangerous — avoid

Reading or writing order data with get_post_meta() / update_post_meta(), or querying wp_posts for shop_order. Under HPOS this silently reads stale data or writes to a table nothing else looks at — the failure mode is data that is subtly wrong, not an error.

What does not change

The WC_Order, WC_Order_Item_*, and WC_Order_Refund APIs are identical in both modes — same getters, same setters, same hooks, same status-transition events. HPOS is a storage-layer change; it is not a new order lifecycle.
