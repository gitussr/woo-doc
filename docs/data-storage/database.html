Data & Storage

Database

How WooCommerce stores data — the WordPress core tables it reuses, the custom tables it adds on top, why the lookup tables exist, and when to query directly versus go through the CRUD layer.

P2 · Advanced DevelopmentAudienceAdvancedStatusDraft · Step 1 foundationApplies toWordPress 7.1 · WooCommerce 11.0.1

WooCommerce's storage is two tiers stacked on each other: WordPress's own tables, which it reuses for content-shaped data, and WooCommerce's own tables, added for the things WordPress has no concept of — order line items, tax rates, sessions, payment tokens, and fast lookup copies of hot fields. Knowing which tier a piece of data lives in is what makes a query correct instead of merely working today.

The full column-by-column listing is the Schema Reference; this page is the map and the judgment calls.

The two tiers

What lives in WordPress's tables

WordPress tableWooCommerce uses it for
wp_postsProducts (product), variations (product_variation), coupons (shop_coupon); legacy-mode orders (shop_order, shop_order_refund)
wp_postmetaProduct fields (_price, _sku, _stock, …), legacy order fields
wp_terms / wp_term_taxonomy / wp_term_relationshipsProduct categories/tags, the internal product_type and product_visibility taxonomies, and one taxonomy per global attribute (pa_*)
wp_users / wp_usermetaCustomer accounts (role customer), billing/shipping address meta
wp_optionsEvery store setting (woocommerce_* keys), most autoloaded

Products are still fundamentally posts. Orders are the exception — see HPOS: a default install stores them in dedicated tables, not wp_posts.

What WooCommerce's own tables hold

Why the lookup tables exist

wp_postmeta and wp_termmeta are schemaless: meta_value is an unindexed-by-value text column, and finding "all in-stock products under $20" means joining several meta rows per product. WooCommerce keeps denormalized, indexed copies of the fields that catalog and reporting queries actually filter and sort on:

Where does this come from?
What am I looking at?
The shop page's price-sorted, in-stock-only product list.
Where does it come from?
Not a live join across wp_postmeta rows — the query hits wc_product_meta_lookup, which has real min_price/max_price and stock_status columns with indexes.
What controls it?
The lookup table's sync, triggered whenever the product is saved.
What can I safely modify?
Read prices/stock through wc_get_product() getters, which are already backed by the lookup table where relevant. Query the lookup table directly only for bulk reporting SQL.
What should I avoid?
Writing to the lookup table directly — it is a cache of postmeta/HPOS data, not the source of truth, and your write will be overwritten on the next sync.

This is the same pattern HPOS applies to the entire order record: replace scattered meta rows with real columns. The product lookup table did it for one entity years earlier.

When to query directly vs. use the CRUD layer

Decision guide

If you are inside normal plugin/theme code touching one or a few records

Always the CRUD layer — wc_get_product(), wc_get_order(), new WC_Customer(). It is correct under both legacy and HPOS storage, and keeps the lookup tables in sync on write.

If you need to aggregate or filter across a large number of records

A direct, read-only query against the appropriate lookup table (wc_product_meta_lookup, the wc_order_*_lookup analytics tables) is the sanctioned fast path — it is what WooCommerce's own reports use.

If you are about to write directly to any WooCommerce or HPOS table

Stop. There is no supported reason to INSERT/UPDATE these tables outside WooCommerce's own code — you will desync the lookup tables, the order tables, or both.

Version-specific · WooCommerce 11.0.1

Table names, prefixes, and columns on this page and the Schema Reference reflect WC_Install::get_schema() and the HPOS orders-table-store definitions for this release. A few tables are feature-gated (created but not populated until the related feature is active) — see the reference page.
