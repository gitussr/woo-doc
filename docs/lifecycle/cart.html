Cart

The cart subsystem — what the cart is (session data, not a table), the shape of a cart item, the totals calculation pipeline and its fixed order of operations, where coupons and fees apply, and how to change a line price correctly.

P1 · Core DevelopmentAudienceIntermediate → AdvancedStatusDraft · Step 1 foundationApplies toWordPress 7.1 · WooCommerce 11.0.1

The cart is the most misunderstood part of WooCommerce. It is not a database table — it is per-visitor session data that is recalculated from scratch on almost every request. Understanding the recalculation pipeline is the key to changing anything about pricing.

What the cart is

Each cart item is an array. The important keys:

KeyHolds
keyThe cart item key — also the array key
product_id, variation_id, variationWhat was added
quantityHow many
dataA live WC_Product object for this line — this is what pricing reads
data_hashA hash of the product data, so a price change invalidates a stale session line
line_subtotal, line_subtotal_tax, line_total, line_tax, line_tax_dataFilled in by the totals pipeline, not by add_to_cart()

The cart item key is md5() of the product id, variation id, variation data, and any extra cart-item data, via WC_Cart::generate_cart_id() — filterable with woocommerce_cart_id. Adding the same product with different custom data (an engraving, a gift note) produces a different key and a separate line.

The totals calculation pipeline

WC()->cart->calculate_totals() runs a fixed sequence. It fires woocommerce_before_calculate_totals, hands the cart to a WC_Cart_Totals instance (the dedicated arithmetic class since WooCommerce 3.2), then fires woocommerce_after_calculate_totals.

Because totals are recomputed every request, anything you change must be re-applied every time calculate_totals() runs — you cannot "set it once". Hook the pipeline, don't patch a stored total.

Coupons

An applied coupon is stored in the session as a code. During calculation WC_Discounts loads each WC_Coupon, validates it against the current cart (usage limits, product/category restrictions, min/max spend, expiry), and applies the discount by discount_type (percent / fixed_cart / fixed_product).

Where does this come from?
What am I looking at?
A discount line in the cart totals.
Where does it come from?
The cart totals template, from $cart->get_coupon_discount_totals(), populated by WC_Discounts during calculate_totals().
What controls it?
The coupon's rules; the validity filters (woocommerce_coupon_is_valid); the discount-amount filters.
What can I safely modify?
Adjust validity with woocommerce_coupon_is_valid; adjust the computed discount with the coupon discount filters; add programmatic discounts as a negative fee.
What should I avoid?
Editing the totals template to fake a discount row without changing the calculated total.

✕Dangerous — avoid

Filtering woocommerce_cart_item_price to show a different number changes the display only. The customer is still charged the calculated total. Value at the calculation layer, formatting at the display layer — never confuse them.

Fragments

The mini-cart / cart-count refresh after AJAX add-to-cart is the fragments system — covered in JavaScript → cart fragments. Its background get_refreshed_fragments request has a real per-page cost on busy stores.

Classic vs Blocks

Classic (PHP templates + hooks)

The [woocommerce_cart] shortcode renders cart/*.php templates. Updates go through wc-ajax (update_shipping_method, apply_coupon, …).

Blocks (Cart/Checkout Blocks)

The Cart Block reads WC()->cart via the Store API (wc/store/v1/cart). Same WC_Cart, same calculate_totals() pipeline underneath — only the presentation and the transport differ.
