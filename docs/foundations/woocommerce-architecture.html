WooCommerce Architecture

How WooCommerce boots inside a WordPress request, the WC() singleton and the objects it holds, the data-store and CRUD layer, and how the cart and session are assembled per visitor.

P0 · EssentialAudienceIntermediate → AdvancedStatusDraft · Step 1 foundationApplies toWordPress 7.1 · WooCommerce 11.0.1

WooCommerce is a large plugin with a deliberate internal shape. Once you can name its main runtime objects and how they are wired together, reading core source — and predicting where your own code should hook — gets much easier.

This page is the architectural overview. Individual subsystems (cart totals, checkout, orders, payments) get their own Architecture pages in later phases.

Bootstrap: from plugin file to WC()

WooCommerce loads like any plugin — its main file runs during the "active plugins load" step of the WordPress request lifecycle. From there it follows a defined sequence:

WooCommerce fires its own actions during this sequence so extensions can hook the right moment:

HookFiresUse it for
woocommerce_loadedOn WordPress plugins_loaded, priority -1 — after every plugin is loaded, before WordPress initCode that needs WooCommerce's classes/functions to exist but must run before init
before_woocommerce_initAt the start of WooCommerce::init() (on WordPress init, priority 0)Declaring feature compatibility — HPOS, Cart/Checkout Blocks
woocommerce_initAt the end of WooCommerce::init(), same tickMost integration setup — factories, post types, and the session now exist
init (WordPress, priority > 0)After WooCommerce::init() has runAnything depending on the product post type or WooCommerce taxonomies

✓Recommended extension point

Declare feature compatibility from a callback on before_woocommerce_init:

The feature slugs are custom_order_tables (HPOS) and cart_checkout_blocks. Declaring later has no effect — the plugin shows as "incompatible" and blocks the merchant from enabling the feature.

The WC() singleton

WC() is a global accessor that returns the one WooCommerce instance. It is the entry point to the main runtime objects:

AccessorIsNotes
WC()->cart (property)WC_CartThe visitor's cart. Loaded on the front end; null on admin / most REST / cron unless wc_load_cart() is called
WC()->session (property)WC_Session_HandlerPer-visitor key/value store backing the cart, coupons, chosen shipping
WC()->customer (property)WC_CustomerCurrent customer — address, tax location, logged-in or guest
WC()->query (property)WC_QueryFront-end query manipulation for shop / product pages
WC()->product_factory / WC()->order_factory (property)factoriesBuild WC_Product / WC_Order objects of the right subclass
WC()->countries (property)WC_CountriesCountry / state lists, address formats, tax base location
WC()->checkout() (method)WC_CheckoutCheckout controller — field definitions, validation, order creation
WC()->mailer() (method)WC_EmailsThe transactional email system
WC()->payment_gateways() (method)WC_Payment_GatewaysRegistry of payment gateways
WC()->shipping() (method)WC_ShippingShipping method / zone registry and package calculation
WC()->queue() (method)Action Scheduler proxySchedule background jobs

WC()->cart and WC()->session are context-sensitive. On admin, cron, and many REST requests they are null or empty because there is no visitor session — WooCommerce::init() only calls initialize_cart() on front-end requests. Code that assumes a cart always exists breaks when it runs in the wrong context.

The practical rules:

✓Recommended extension point

Read and write WooCommerce entities through their CRUD class: wc_get_product( $id ), wc_get_order( $id ), new WC_Customer( $id ). Call ->save() once after setting values. This stays correct across HPOS and future storage changes.

✕Dangerous — avoid

Writing directly to wp_postmeta for orders, or assuming a specific table layout. Under HPOS the write goes to the wrong place or is silently ignored, and reports/emails then disagree with the database.

Sessions

For anything that must persist across requests but is not a user account — the guest cart, applied coupons, chosen shipping method, checkout progress — WooCommerce uses its own session, separate from PHP sessions.

Version-specific · WooCommerce 11.0.1

11.0.1 moved guest session cookies to a stronger, salted hashing scheme (with backward compatibility for existing cookies). The table name and the woocommerce_cleanup_sessions schedule are unchanged.

Full-page caching and sessions interact badly if misconfigured: a cached page can show one visitor's cart count to another. Hosts and caching plugins normally exclude cart/checkout/account pages and vary on the session cookie. This gets a full treatment in the Performance section (planned).

Classic and Blocks are two front-ends on one core

A recurring architectural fact: the data and business logic layer is shared, but the storefront presentation exists in two implementations.

Classic (PHP templates + hooks)

Shortcodes and PHP templates render cart/checkout. Server-rendered, driven by admin-ajax and classic template hooks. The path most existing code targets.

Blocks (Cart/Checkout Blocks)

React components render cart/checkout, talking to the Store API. Customized through block settings, Slot/Fill, and integration interfaces — not PHP template hooks.

Both ultimately call the same WC()->cart, the same totals calculation, and the same order-creation code. The split is at the edge, not the core — which is why "change the value in core logic, change the presentation per front-end" is the reliable customization strategy.

Version-specific · WooCommerce 11.0.1

Since WooCommerce 8.3 the Cart, Checkout, and Order Confirmation Blocks are the default on new installs. Stores created before 8.3 keep the classic shortcode pages until a merchant migrates them (WooCommerce → Status → Tools). So a given store can be on either front-end — never assume.
