REST API

WooCommerce's two HTTP APIs — the wc/v3 REST API for server-to-server integration and the wc/store/v1 Store API for the browser — their auth models, how to add custom routes, and when to use which.

P1 · Core DevelopmentAudienceIntermediate → AdvancedStatusDraft · Step 1 foundationApplies toWordPress 7.1 · WooCommerce 11.0.1

WooCommerce exposes two HTTP APIs built on the WordPress REST infrastructure (/wp-json/). They look similar and are used for opposite purposes.

wc/v3 REST API

Base: /wp-json/wc/v3/. Main resources:

RoutePurpose
products, products/<id>/variations, products/categories, products/tags, products/attributes, products/reviewsCatalog CRUD
orders, orders/<id>/notes, orders/<id>/refundsOrder CRUD and history
customersCustomer records
couponsCoupon CRUD
reports/*Legacy report summaries
tax_classes, taxesTax config
shipping/zones, shipping_methods, payment_gatewaysFulfilment / payment config
webhooksOutbound webhook subscriptions
settings/<group>, system_status, data/*Store config, the status report as JSON, reference data

The Analytics reports live under a separate namespace, /wp-json/wc-analytics/… (reports/orders, reports/products, reports/revenue, …), plus imports/status and imports/retry-failed added in WooCommerce 11.0 for managing failed historical-data imports.

Auth

  • API keys — generated at WooCommerce → Settings → Advanced → REST API, as a consumer key / consumer secret pair with a Read / Write / Read-Write scope. Sent over HTTPS as HTTP Basic auth or as query parameters on non-HTTPS (discouraged).
  • Cookie auth + nonce — for same-origin requests from a logged-in admin (e.g. a custom admin screen), send the X-WP-Nonce header from wp_create_nonce( 'wp_rest' ).

!Possible, but has maintenance cost

API keys are full credentials for whatever scope they carry. A Read-Write key can create orders and read every customer's PII. Scope them minimally, store them as secrets, and revoke unused ones.

Store API

Base: /wp-json/wc/store/v1/. Main endpoints: cart, cart/add-item, cart/update-item, cart/remove-item, cart/apply-coupon, cart/remove-coupon, cart/update-customer, cart/select-shipping-rate, cart/extensions, checkout, batch, products, products/attributes, products/categories, products/collection-data, products/reviews.

It is stateful: a Cart-Token header (a JWT, returned on the first GET /cart response) identifies the WooCommerce session, so POST wc/store/v1/cart/add-item mutates this visitor's cart. POST to /cart/* and all /checkout requests also require a Nonce header — unless a Cart-Token is supplied, in which case the nonce is not needed. This is why the Store API is safe to call from the browser and is not a general integration API.

Extend it with ExtendSchema rather than raw filters — see Blocks → server side.

Adding a custom route

Neither API is designed for you to bolt resources onto. For custom endpoints, register your own namespace with WordPress core's register_rest_route():

✕Dangerous — avoid

A route with 'permission_callback' => '__return_true' is public. If it reads or writes store data, that is a data-exposure bug. Always supply a real permission callback.

You can reuse WooCommerce's CRUD objects (wc_get_product(), wc_get_order()) inside your callback — do not query tables directly.

Which to use

Decision guide

If an external system syncs products/orders
wc/v3 with a scoped API key.
If a browser needs to read or change the current cart
Store API (wc/store/v1).
If you built a headless storefront
Store API for cart/checkout, wc/v3 (server-side only) for catalog and account data.
If you need a bespoke operation
Your own register_rest_route() namespace with a permission callback.
