Templates

The classic WooCommerce template system — how templates are located and loaded, the theme override mechanism, template parts, the variables in scope inside a template, the hooks fired from within them, and when not to override.

P1 · Core DevelopmentAudienceIntermediateStatusDraft · Step 1 foundationApplies toWordPress 7.1 · WooCommerce 11.0.1

WooCommerce's classic storefront is rendered from PHP template files. A theme can replace any of them by providing its own copy. This is powerful and frequently the wrong first choice — a hook or filter usually reaches what you need without the maintenance cost.

Templates apply to the classic front-end only. The Cart and Checkout Blocks do not use them.

How a template is located

Core renders a fragment by calling wc_get_template() or wc_get_template_part(), which delegate path resolution to wc_locate_template():

Overriding a template in a theme

  1. Find the source file under plugins/woocommerce/templates/ — e.g. templates/single-product/title.php.
  2. Copy it to your theme, dropping the templates/ segment and adding a woocommerce/ prefix: your-child-theme/woocommerce/single-product/title.php.
  3. Edit your copy.

!Possible, but has maintenance cost

You now maintain a fork of that file. Each core template has an @version docblock; WooCommerce → Status → System Status lists every override whose version is behind core ("version X is out of date. The core version is Y"). When it flags one, diff your copy against the new core file and re-apply your change. A stale override silently drops new markup, hooks, and accessibility fixes.

✓Recommended extension point

Before copying a template, check whether an action hook inside it, or a filter on the value it prints, does the job. Overriding price.php to change a price is almost always wrong — filter woocommerce_get_price_html instead.

A plugin can provide templates too

The signature is wc_get_template( $template_name, $args = array(), $template_path = '', $default_path = '' ). A plugin that calls wc_get_template( 'foo.php', $args, '', plugin_dir_path( __FILE__ ) . 'templates/' ) ships its own default while wc_locate_template() still checks the theme's woocommerce/foo.php first — so themes can override plugin-provided templates exactly as they override core ones.

Variables in scope

wc_get_template( $name, $args ) runs extract( $args ) before including the file, so each key of $args becomes a local variable. Which keys exist is per template — read the wc_get_template() call in core that renders it.

Common examples:

TemplateIn scope
single-product/*.php$product (the global $product is also set)
cart/cart.phpno $args; reads WC()->cart directly
checkout/form-checkout.php$checkout (a WC_Checkout instance)
emails/email-order-details.php$order, $sent_to_admin, $plain_text, $email
cart/cart-totals.php, checkout/review-order.phpno $args; read WC()->cart

Each core template's docblock lists what it can rely on; the wc_get_template() call site is the authoritative source.

Template parts and hooks inside templates

  • wc_get_template_part( $slug, $name ) loads content templates like content-product.php from the loop. Themes override these the same way.
  • Templates contain do_action() calls — these are the injection points you should prefer over editing the file. content-single-product.php is almost entirely do_action( 'woocommerce_single_product_summary' ) and siblings; the markup lives in hooked callbacks, not the template.

If you keep a template override, keep its do_action() calls. Removing them silently disables every plugin (and core feature) that injects there.

When not to override

Decision guide

If a filter changes the value
Filter it. No override.
If an action hook inside the template reaches the position
Hook it. No override.
If you need structural markup changes a hook cannot make, on the classic front-end
Override — and register it in System Status review.
If the store uses the Cart/Checkout Blocks
Overriding cart/ or checkout/ templates does nothing. Use the Blocks APIs.
