About WooDoc

Information Architecture

The full WooDoc documentation map — every planned section with its purpose, audience, priority, what belongs there, and what does not.

P0 · EssentialAudienceContributors & stakeholdersStatusLiving structure · not a final commitmentApplies toWordPress 7.1 · WooCommerce 11.0.1

This is the living architecture of WooDoc. It is designed for searchability and discoverability: a developer should be able to predict which section a topic lives in.

Only a few pages exist today (see Roadmap). This page defines the shape everything else will fill.

Priority levels

WooDoc tags pages with a priority so contributors and readers know what is foundational versus specialized.

LevelMeaning
P0 · EssentialA developer cannot properly understand WooCommerce without this.
P1 · Core DevelopmentImportant for day-to-day WooCommerce development.
P2 · Advanced DevelopmentImportant for deeper customization and architecture.
P3 · SpecializedUseful for advanced or niche scenarios.
P4 · ReferenceDeep technical / reference lookup material.

The tree

This structure will change as WooDoc grows. Simplified diagrams get replaced with accurate architecture diagrams; sections split or merge as content arrives. Do not treat it as final.

Section reference

Introduction

  • Purpose — orient a WordPress developer: what WooCommerce is, why it exists, how it differs from plain WordPress work, and how to think about it.
  • Audience — beginner to intermediate.
  • Priority — P0 · Essential
  • Belongs here — conceptual framing, the "why", the mental model, the "where does this come from?" pattern.
  • Does not belong here — API reference, step-by-step configuration, code recipes.

Foundations

  • Purpose — the load-bearing concepts: the WordPress features WooCommerce builds on, WooCommerce's own architecture, its data model, and its extension model.
  • Audience — intermediate; advanced for the architecture depth.
  • Priority — P0 · Essential to P1 · Core Development
  • Belongs here — how the request lifecycle works, how data stores and CRUD classes are organized, how hooks/filters/templates/blocks fit together as an extension system.
  • Does not belong here — task guides, admin walkthroughs, per-feature reference (those live in the feature sections).

Store Setup

  • Purpose — the admin-facing configuration surface: settings, and the setup of products, customers, orders, payments, shipping, and taxes.
  • Audience — beginner to intermediate.
  • Priority — P1 · Core Development
  • Belongs here — what each settings screen controls, how configuration maps to stored options, and the developer-relevant consequences of each choice.
  • Does not belong here — deep internals and extension development (those live in the matching feature section and in Development).

Development

  • Purpose — the extension toolkit: hooks, filters, templates, shortcodes, blocks, AJAX, REST, and JavaScript — how each mechanism works and when to reach for it.
  • Audience — intermediate to advanced.
  • Priority — P1 · Core Development to P2 · Advanced Development
  • Belongs here — the mechanics of each extension point, safety levels, and cross-cutting patterns (plugin vs mu-plugin vs theme, enqueueing, nonce handling).
  • Does not belong here — exhaustive per-hook catalog entries (those are reference pages under the relevant feature section, tagged P4 · Reference).

Commerce Lifecycle — Products, Cart, Checkout, Orders, Payments, Shipping & Tax, Emails

  • Purpose — one deep, self-contained treatment per subsystem: what it is, where it lives, its lifecycle, its data, its hooks/filters/templates/blocks, its gotchas, and its safe customization patterns. (Customers is currently folded into Checkout and Orders; it may get its own page later.)
  • Audience — intermediate to advanced.
  • Priority — P1 · Core Development for the concepts, P4 · Reference for the reference tables within them.
  • Belongs here — the full "where does this come from?" treatment for every significant element of that subsystem, plus classic-vs-Blocks notes.
  • Does not belong here — generic extension mechanics (link to Development instead), unrelated subsystems.

Data & Storage — Database, HPOS, Schema Reference

  • Purpose — how WooCommerce stores data: core WordPress tables it uses, WooCommerce's custom tables, meta usage, query patterns, and a full column-by-column schema lookup.
  • Audience — advanced.
  • Priority — P2 · Advanced Development concepts, P4 · Reference schema reference.
  • Belongs here — table purposes, relationships, when to query directly vs use CRUD classes, and migration/compatibility notes.
  • Does not belong here — HPOS specifics (its own page below), ORM-style tutorials unrelated to WooCommerce.

HPOS (High-Performance Order Storage)

  • Purpose — how order storage works with HPOS: the tables, the compatibility mode, the migration, and what changes for developers.
  • Audience — intermediate to advanced.
  • Priority — P1 · Core Development
  • Belongs here — the order data model under HPOS, how to write code that works in both modes, and the sync/compatibility behavior.
  • Does not belong here — general order lifecycle (that is Orders), generic database theory.

Customization

  • Purpose — cross-cutting "how to change X safely" patterns that span multiple subsystems.
  • Audience — intermediate to advanced.
  • Priority — P1 · Core Development
  • Belongs here — template override strategy, when to build a plugin, child-theme boundaries, Blocks customization patterns, and the safety-level framework applied to real scenarios.
  • Does not belong here — subsystem-specific recipes (those live with the subsystem).

Debugging

  • Purpose — how to diagnose unexpected WooCommerce behavior methodically.
  • Audience — all levels.
  • Priority — P1 · Core Development
  • Belongs here — logging, the status report, hook tracing, isolating plugin conflicts, reading the calculation pipeline, and common failure signatures with their causes.
  • Does not belong here — feature documentation; link back to the subsystem being debugged.

Performance

  • Purpose — where WooCommerce spends time and how to reduce it.
  • Audience — advanced.
  • Priority — P2 · Advanced Development
  • Belongs here — object caching, autoloaded options, query cost, cart fragment cost, extension overhead, and headless considerations.
  • Does not belong here — generic web performance advice unrelated to WooCommerce.

Security

  • Purpose — the WooCommerce-specific security surface.
  • Audience — intermediate to advanced.
  • Priority — P2 · Advanced Development
  • Belongs here — nonces and capability checks in custom code, handling PII in orders and customers, payment data boundaries, and safe AJAX/REST patterns.
  • Does not belong here — general WordPress hardening (link out), server configuration.

Limitations

  • Purpose — an honest catalog of what WooCommerce does not do well, and when to choose another approach.
  • Audience — all levels; especially decision-makers.
  • Priority — P1 · Core Development
  • Belongs here — architectural constraints, the CMS-shaped data model, scaling ceilings, and decision guides comparing WooCommerce to custom builds and other platforms.
  • Does not belong here — feature wishlists framed as bugs.

How this maps to the current site

Today, WooDoc ships Introduction, Foundations, Development, Commerce Lifecycle, Data & Storage, Customization, Debugging, Performance, Security, and this About WooDoc section. A dedicated Customers page and Limitations in the tree above are planned. The Roadmap sequences the build.
