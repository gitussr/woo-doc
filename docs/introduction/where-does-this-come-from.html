Introduction

Where Does This Come From?

WooDoc's signature pattern for tracing any WooCommerce element back to the layer that produced it — and deciding where it is safe to change.

P0 · EssentialAudienceBeginner → AdvancedStatusDraft · Step 1 foundationApplies toWordPress 7.1 · WooCommerce 11.0.1

This is the pattern WooDoc is built around. When you see any WooCommerce element — a button, a field, a line of totals, a message, an email — you should be able to walk a short, repeatable path from "what is this?" to "where do I safely change it?".

Later steps of WooDoc apply this pattern to concrete elements (the add-to-cart button, checkout fields, order-status emails, and so on). This page teaches the pattern itself.

The five questions

Walking each question

1. What am I looking at?

Name the element precisely. "The price" is ambiguous; "the sale price shown on the single product page" is not. Is it text, a form control, a link, a computed value, a status message?

2. Where does it come from?

Identify the layer that emitted it:

Practical tells: view source vs. inspect the live DOM (a difference means JS or AJAX built it); search the WooCommerce templates/ directory for visible static text; check whether the value changes without a full page reload (fragments / Blocks).

3. What controls it?

Once you know the layer, find the specific control point: the template file and the hook fired inside it, the filter applied to the value, the block and its settings, or the script and the endpoint it calls.

4. What can I safely modify?

Map the control point to a safety level:

✓Recommended extension point

There is a hook or filter for exactly this. Use it from a plugin or mu-plugin. First choice, every time.

!Possible, but has maintenance cost

No hook reaches it, but the template can be overridden in your theme, or a block exposes a Slot/Fill. Acceptable — record that you now maintain that override against future WooCommerce updates.

✕Dangerous — avoid

The only way to change it is editing a core file or relying on an internal that has no stability promise. Stop and find another approach.

5. What should I avoid?

State the thing not to do and why: do not edit the core template in place; do not change the displayed value without changing the calculated value; do not hook a stage that does not fire under the active cart/checkout implementation.

Worked shape (illustrative)

Where does this come from?
What am I looking at?
The "Add to cart" button on a single product page.
Where does it come from?
The woocommerce_single_product_summary action runswoocommerce_template_single_add_to_cart at priority 30, which loads single-product/add-to-cart/<type>.php(simple.php, variable.php, …) viawc_get_template().
What controls it?
The hook that prints the form, filters on the button text and URL, and the product's type/purchasability. On AJAX-enabled archives, a script also intercepts the click.
What can I safely modify?
Filter the button text or URL; add markup via the surrounding action hooks; enqueue your own script for behavior. All from a plugin.
What should I avoid?
Editing single-product/add-to-cart/*.php in the WooCommerce plugin directory; assuming the archive button and the single-product button share one code path.
Version-specific · WooCommerce 11.0.1

The concrete file paths, hook names, and script handles referenced across WooDoc are being verified against this version. Anything not yet confirmed is marked with a ⚠verify tag.

Why this pattern matters

It converts "WooCommerce is a black box" into a finite lookup. You are never guessing — you are walking layers from output back to source, and stopping at the safest one that can do the job.
