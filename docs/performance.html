Performance

Where WooCommerce spends time and how to reduce it — object caching and sessions, autoloaded options, query and fragment cost, extension overhead, and headless considerations.

P2 · Advanced DevelopmentAudienceAdvancedStatusDraft · Step 1 foundationApplies toWordPress 7.1 · WooCommerce 11.0.1

WooCommerce's performance story is mostly about avoiding unindexed lookups and unnecessary per-request work — several of the mechanisms that exist for correctness (sessions, lookup tables, cart fragments) also happen to be the biggest cost centers if left unmanaged. This page connects those dots rather than re-deriving them; each links to where the mechanism is documented in full.

Object caching and sessions

WordPress's object cache (transient/wp_cache_* API) is a no-op back end by default — wp_cache_set() still "works" but nothing survives past the request unless a persistent object cache (Redis, Memcached) is installed.

✓Recommended extension point

Run a persistent object cache on any store with real traffic. WooCommerce reads and writes the customer's session (woocommerce_sessions — see Database) on nearly every request that has a non-empty cart; without a persistent object cache, session storage falls back to a database row read/write on every single one of those requests.

Autoloaded options

Every wp_options row with autoload = 'yes' is loaded into memory on every WordPress request, admin or front-end, whether that request needs it or not. wp_options has no index on autoload, so this scan itself gets more expensive as the table grows.

WooCommerce and its extensions are frequent contributors: large serialized settings arrays, cached API responses stored as options instead of transients, and (particularly) session and rate-limit rows that should never have been autoloaded in the first place.

Where does this come from?
What am I looking at?
A store that feels slow specifically in **wp-admin**, more than on the front end.
Where does it come from?
wp-admin is largely uncached, so it pays the full autoloaded-options cost on every screen load — a front-end page behind a page cache does not.
What controls it?
Every plugin (including WooCommerce and its extensions) that calls `update_option()` without explicitly passing `false` for autoload.
What can I safely modify?
Audit total autoloaded size (`SELECT SUM(LENGTH(option_value)) FROM wp_options WHERE autoload = 'yes'`) periodically; report an oversized option to the extension that owns it.
What should I avoid?
Flipping autoload to `no` on an option a plugin still expects to be autoloaded — that just moves the same query cost into the request path it runs in, or breaks logic that assumed the value was already in memory.

Query and fragment cost

Two mechanisms exist specifically because a naive WordPress query was too slow at scale, and both still have a residual cost to manage:

Extension overhead

A filter or action that runs once per product in a loop — a catalog page, a cart with many line items, an export — turns any per-call cost (an uncached query, an external API call, expensive string formatting) into an N+1 problem invisible in isolation but severe at scale.

!Possible, but has maintenance cost

Profile with Query Monitor (or equivalent) on a shop/category page with a realistic product count before shipping a filter on woocommerce_get_price_html, woocommerce_product_get_price, or any other filter that fires per product in a loop. A single added query there is one query times every product on the page.

Headless considerations

A headless build talks to WooCommerce entirely through the Store API — the classic wc-ajax/cart-fragments machinery does not apply, since there is no server-rendered page for it to refresh. The relevant costs shift to:

  • Cart/session continuity — the Store API identifies a cart by a Cart-Token: an HS256 JWT (Automattic\WooCommerce\StoreApi\Utilities\JsonWebToken), signed with a secret derived from wp_salt(), carrying the customer/session id and an exp claim set to issue time + DAY_IN_SECONDS * 2 (48 hours, filterable via wc_session_expiration) — rather than a PHP session cookie. The client is responsible for persisting it and resending it as the Cart-Token request header on every call; there is no separate refresh endpoint, so a headless client needs to fetch a fresh cart (and token) once the old one expires.
  • No fragment cache to lean on — every cart/checkout render is a fresh API call; caching strategy has to be built into the headless front end itself rather than inherited from server-rendered fragments.
