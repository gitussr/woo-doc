WooCommerce exposes **two** HTTP APIs built on the WordPress REST
infrastructure (`/wp-json/`). They look similar and are used for opposite
purposes.

<LayerStack
  layers={[
    { name: 'wc/v3 — REST API', note: 'Server-to-server. Full CRUD on stored records: products, orders, customers, coupons, refunds, reports, settings, webhooks. Authenticated with API keys. Not for the browser.' },
    { name: 'wc/store/v1 — Store API', note: 'Browser-facing. Manages the session cart and drives the Cart/Checkout Blocks. Authenticated with a cart token / nonce, no API keys. Read-heavy public product data plus cart/checkout mutation.' },
  ]}

## wc/v3 REST API

Base: `/wp-json/wc/v3/`. Main resources:

| Route | Purpose |
| --- | --- |
| `products`, `products/<id>/variations`, `products/categories`, `products/tags`, `products/attributes`, `products/reviews` | Catalog CRUD |
| `orders`, `orders/<id>/notes`, `orders/<id>/refunds` | Order CRUD and history |
| `customers` | Customer records |
| `coupons` | Coupon CRUD |
| `reports/*` | Legacy report summaries |
| `tax_classes`, `taxes` | Tax config |
| `shipping/zones`, `shipping_methods`, `payment_gateways` | Fulfilment / payment config |
| `webhooks` | Outbound webhook subscriptions |
| `settings/<group>`, `system_status`, `data/*` | Store config, the status report as JSON, reference data |

The **Analytics** reports live under a separate namespace,
`/wp-json/wc-analytics/…` (`reports/orders`, `reports/products`,
`reports/revenue`, …), plus `imports/status` and `imports/retry-failed` added
in WooCommerce 11.0 for managing failed historical-data imports.

### Auth

- **API keys** — generated at WooCommerce → Settings → Advanced → REST API, as
  a consumer key / consumer secret pair with a Read / Write / Read-Write
  scope. Sent over HTTPS as HTTP Basic auth or as query parameters on
  non-HTTPS (discouraged).
- **Cookie auth + nonce** — for same-origin requests from a logged-in admin
  (e.g. a custom admin screen), send the `X-WP-Nonce` header from
  `wp_create_nonce( 'wp_rest' )`.

<SafetyLevel level="risky">
  API keys are full credentials for whatever scope they carry. A Read-Write
  key can create orders and read every customer's PII. Scope them minimally,
  store them as secrets, and revoke unused ones.
</SafetyLevel>

## Store API

Base: `/wp-json/wc/store/v1/`. Main endpoints: `cart`, `cart/add-item`,
`cart/update-item`, `cart/remove-item`, `cart/apply-coupon`,
`cart/remove-coupon`, `cart/update-customer`, `cart/select-shipping-rate`,
`cart/extensions`, `checkout`, `batch`, `products`, `products/attributes`,
`products/categories`, `products/collection-data`, `products/reviews`.

It is **stateful**: a **`Cart-Token`** header (a JWT, returned on the first
`GET /cart` response) identifies the
[WooCommerce session](/docs/foundations/woocommerce-architecture#sessions), so
`POST wc/store/v1/cart/add-item` mutates *this visitor's* cart. `POST` to
`/cart/*` and all `/checkout` requests also require a **`Nonce`** header —
unless a `Cart-Token` is supplied, in which case the nonce is not needed.
This is why the Store API is safe to call from the browser and is not a
general integration API.

Extend it with `ExtendSchema` rather than raw filters — see
[Blocks → server side](/docs/development/blocks#server-side-attach-and-receive-data).

## Adding a custom route

Neither API is designed for you to bolt resources onto. For custom endpoints,
register your own namespace with WordPress core's `register_rest_route()`:

```php
add_action( 'rest_api_init', function () {
    register_rest_route( 'wd/v1', '/stock-alert', array(
        'methods'             => 'POST',
        'callback'            => 'wd_stock_alert',
        'permission_callback' => fn() => current_user_can( 'manage_woocommerce' ),
        'args'                => array(
            'product_id' => array( 'required' => true, 'sanitize_callback' => 'absint' ),
        ),
    ) );
} );
```

<SafetyLevel level="dangerous">
  A route with <code>'permission_callback' =&gt; '__return_true'</code> is
  public. If it reads or writes store data, that is a data-exposure bug.
  Always supply a real permission callback.
</SafetyLevel>

You can reuse WooCommerce's CRUD objects (`wc_get_product()`,
`wc_get_order()`) inside your callback — do not query tables directly.

## Which to use

<DecisionGuide>
  <Choice when="an external system syncs products/orders">`wc/v3` with a scoped API key.</Choice>
  <Choice when="a browser needs to read or change the current cart">Store API (`wc/store/v1`).</Choice>
  <Choice when="you built a headless storefront">Store API for cart/checkout, `wc/v3` (server-side only) for catalog and account data.</Choice>
  <Choice when="you need a bespoke operation">Your own `register_rest_route()` namespace with a permission callback.</Choice>
</DecisionGuide>
