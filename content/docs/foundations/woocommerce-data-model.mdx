<PageMeta priority="P0" audience="Intermediate → Advanced" />

WooCommerce's data model is a commerce domain expressed in WordPress's
storage. Some entities are custom post types; some are custom tables; order
storage is currently mid-migration between the two. This page is the map.

Read [WooCommerce Architecture](/docs/foundations/woocommerce-architecture#the-data-layer-crud-classes-and-data-stores)
first if you have not — the CRUD-class-over-data-store pattern is what makes
this model workable.

## Products

A product is the most WordPress-shaped entity: a `product` post plus a lot of
meta plus taxonomy terms.

<LayerStack
  layers={[
    { name: 'wp_posts (type product)', note: 'title, description (post_content), short description (post_excerpt), status, slug' },
    { name: 'wp_postmeta', note: 'price, SKU, stock, weight, dimensions, tax class, and most other fields — as underscore-prefixed keys' },
    { name: 'Product meta lookup table', note: 'a flattened copy of hot fields (price, stock status, rating) that catalog queries use instead of postmeta' },
    { name: 'Taxonomies', note: 'product_cat, product_tag, and one taxonomy per global attribute (pa_color, pa_size, …)' },
    { name: 'wp_posts (type product_variation)', note: 'one child post per variation of a variable product, each with its own price/stock meta' },
  ]}
/>

Product **types** are represented by CRUD subclasses selected from a taxonomy
term (`product_type`): simple, variable, grouped, external/affiliate, plus
whatever extensions add (subscription, bundle, …).

<VerifyNote>the `product_type` taxonomy mechanism, the built-in type list, the core product meta keys, and the product meta lookup table name/columns for 11.0.1</VerifyNote>

<SafetyLevel level="recommended">
  <code>$product = wc_get_product( $id );</code> then
  <code>$product-&gt;get_price()</code>, <code>-&gt;get_stock_quantity()</code>,
  <code>-&gt;is_in_stock()</code>. The getters read from the right place
  (lookup table, meta, or computed) — raw meta reads do not.
</SafetyLevel>

## Orders and order items

An order is a container; the money and the goods live in its **items**. Even
under classic storage, order items were never post meta — they have always
been in dedicated tables.

<LayerStack
  layers={[
    { name: 'Order record', note: 'status, currency, customer ID, totals, dates, billing/shipping address. Classic: shop_order post + postmeta. HPOS: wc_orders + wc_order_addresses + wc_order_operational_data + wc_orders_meta.' },
    { name: 'Order items table', note: 'one row per line — a product line, a shipping line, a fee, a coupon, a tax line. Each row has a type.' },
    { name: 'Order item meta table', note: 'per-item detail: which product/variation, quantity, line subtotal/total, tax amounts, chosen variation attributes.' },
  ]}
  caption="Order storage. The item and item-meta tables are shared between classic and HPOS; only the order record itself moves."
/>

<VerifyNote>the HPOS table names (`wc_orders`, `wc_orders_meta`, `wc_order_addresses`, `wc_order_operational_data`?), the order items tables (`wp_woocommerce_order_items`, `wp_woocommerce_order_itemmeta`?), and the item `order_item_type` values for 11.0.1</VerifyNote>

### Classic vs HPOS storage

<ClassicVsBlocks
  classic="Order = a shop_order post in wp_posts; its fields are rows in wp_postmeta. Queryable with WP_Query and get_posts(). This was the default for years."
  blocks="HPOS: order = rows in purpose-built wc_order* tables with real columns and indexes. Queried with wc_get_orders() / the orders data store. Much faster for large order volumes."
/>

<Callout type="warn">
  A store can run in **HPOS mode**, **legacy posts mode**, or a
  **compatibility (sync) mode** that writes both. Code that must work
  everywhere reads and writes only through `wc_get_order()` / `WC_Order` and
  queries only through `wc_get_orders()` — never `WP_Query` for orders, never
  direct SQL against a hard-coded table. HPOS gets its own section in a later
  phase.
</Callout>

<VerifyNote>the exact names of the three HPOS modes and the current default for new installs in 11.0.1</VerifyNote>

## Customers

"Customer" is two things wearing one CRUD class:

<DecisionGuide>
  <Choice when="the buyer has an account">
    A WordPress user (role `customer`), plus WooCommerce meta for
    billing/shipping address, and a lookup-table row for reporting. Order
    history is every order with their user ID.
  </Choice>
  <Choice when="the buyer checked out as a guest">
    No user row. The customer exists only as the address data stored *on the
    order*, plus a transient `WC_Customer` built from the session during
    checkout. Matched to future orders only by email, heuristically.
  </Choice>
</DecisionGuide>

<VerifyNote>the customer lookup table name, the `customer` role capabilities, and how guest customers appear in Analytics for 11.0.1</VerifyNote>

## Coupons

A coupon is a `shop_coupon` post whose meta holds the rule: discount type
(percentage, fixed cart, fixed product), amount, usage limits, product/
category restrictions, expiry, minimum/maximum spend. `WC_Coupon` reads it;
the cart totals pipeline applies it.

<VerifyNote>the coupon meta keys and discount-type slugs for 11.0.1</VerifyNote>
