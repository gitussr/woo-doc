<PageMeta priority="P0" audience="Intermediate → Advanced" />

WooCommerce's data model is a commerce domain expressed in WordPress's
storage. Some entities are custom post types; some are custom tables; order
storage is currently mid-migration between the two. This page is the map.

Read [WooCommerce Architecture](/docs/foundations/woocommerce-architecture#the-data-layer-crud-classes-and-data-stores)
first if you have not — the CRUD-class-over-data-store pattern is what makes
this model workable.

## The entities at a glance

| Entity | CRUD class | Storage |
| --- | --- | --- |
| Product | `WC_Product` + `WC_Product_Simple` / `WC_Product_Variable` / `WC_Product_Grouped` / `WC_Product_External` | Post type `product` |
| Product variation | `WC_Product_Variation` | Post type `product_variation`, child of a `product` |
| Order | `WC_Order` (extends `WC_Abstract_Order`) | HPOS: `wc_order*` tables. Legacy: post type `shop_order` |
| Order item | `WC_Order_Item_Product` / `_Shipping` / `_Fee` / `_Coupon` / `_Tax` (extend `WC_Order_Item`) | `woocommerce_order_items` + `woocommerce_order_itemmeta` |
| Refund | `WC_Order_Refund` | Like an order; post type `shop_order_refund` in legacy mode |
| Customer | `WC_Customer` | WP user with role `customer`, or a guest (session + order only) |
| Coupon | `WC_Coupon` | Post type `shop_coupon` |

All the product and order classes ultimately extend `WC_Data`, the base class
that provides the getter/setter/`save()` contract and delegates persistence to
a data store.

## Products

A product is the most WordPress-shaped entity: a `product` post plus a lot of
meta plus taxonomy terms.

    { name: 'wp_postmeta', note: 'fields as underscore-prefixed keys: _regular_price, _sale_price, _price, _sku, _stock, _stock_status, _weight, _length/_width/_height, _tax_class, _manage_stock, _downloadable, _virtual' },

    { name: 'wp_posts (type product_variation)', note: 'one child post per variation of a variable product, each with its own price/stock meta and an attribute_* meta key per attribute' },
  ]}
/>

Product **types** are set by the `product_type` taxonomy term on the product
(`public => false`, `hierarchical => false`). The built-in terms are
**`simple`**, **`variable`**, **`grouped`**, and **`external`** (external /
affiliate); each maps to a `WC_Product_*` subclass. Extensions register more
(`subscription`, `bundle`, `composite`, …) by adding a term and filtering the
class map (`woocommerce_product_class` / `woocommerce_product_type_query`).

<SafetyLevel level="recommended">
  <code>$product = wc_get_product( $id );</code> then
  <code>$product-&gt;get_price()</code>, <code>-&gt;get_stock_quantity()</code>,
  <code>-&gt;is_in_stock()</code>. The getters read from the right place
  (lookup table, meta, or computed) — raw meta reads do not.
</SafetyLevel>

## Orders and order items

An order is a container; the money and the goods live in its **items**. Even
under classic storage, order items were never post meta — they have always
been in dedicated tables.

### Classic vs HPOS storage

<Callout type="warn">
  HPOS ("High-Performance Order Storage") settings offer three states:
  **"WordPress post tables"** (legacy), **"High-performance order storage"**,
  and legacy **with "compatibility mode"** enabled, which syncs writes to both.
  HPOS has been the default for **new** installs since WooCommerce 8.2;
  pre-8.2 stores stay on post tables until migrated. Code that must work
  everywhere reads and writes only through `wc_get_order()` / `WC_Order`,
  queries only through `wc_get_orders()`, and never runs `WP_Query` or direct
  SQL against a hard-coded order table. Internally,
  `WC_Data_Store::load( 'order' )` returns `OrdersTableDataStore` or
  `WC_Order_Data_Store_CPT` depending on which tables are authoritative. HPOS
  gets its own section in a later phase.
</Callout>

## Customers

"Customer" is two things wearing one CRUD class:

<DecisionGuide>
  <Choice when="the buyer has an account">
    A WordPress user with role `customer` (capabilities: `read` plus
    WooCommerce's own `read_private_shop_orders` etc. for their own data),
    plus user meta for billing/shipping address, plus a row in
    `wp_wc_customer_lookup` for Analytics. Order history is every order with
    their `customer_id`.
  </Choice>
  <Choice when="the buyer checked out as a guest">
    No user row. The customer exists only as the address copied *onto the
    order*, plus a transient `WC_Customer` built from the session during
    checkout. Analytics still gets a `wp_wc_customer_lookup` row, keyed by
    email with `user_id = 0`, so guest orders are attributed.
  </Choice>
</DecisionGuide>

<VersionNote version="WooCommerce 11.0">
  11.0 added **guest order claiming**: a logged-in customer can link past
  guest-checkout orders (matched by email, with email verification) to their
  account, after which those orders show in their order history.
</VersionNote>

## Coupons

A coupon is a `shop_coupon` post whose meta holds the rule. The
`discount_type` is one of `percent`, `fixed_cart`, or `fixed_product`; other
meta keys include `coupon_amount`, `individual_use`, `usage_limit`,
`usage_limit_per_user`, `limit_usage_to_x_items`, `date_expires`,
`free_shipping`, `product_ids` / `exclude_product_ids`, `product_categories` /
`exclude_product_categories`, `minimum_amount`, `maximum_amount`. `WC_Coupon`
reads it; the cart totals pipeline applies it.
