WooCommerce is a large plugin with a deliberate internal shape. Once you can
name its main runtime objects and how they are wired together, reading core
source — and predicting where your own code should hook — gets much easier.

This page is the architectural overview. Individual subsystems (cart totals,
checkout, orders, payments) get their own [Architecture](/docs/about/design-system)
pages in later phases.

## Bootstrap: from plugin file to `WC()`

WooCommerce loads like any plugin — its main file runs during the "active
plugins load" step of the [WordPress request lifecycle](/docs/foundations/wordpress-fundamentals#the-request-lifecycle).
From there it follows a defined sequence:

<Lifecycle
  steps={[
    'woocommerce.php runs during plugin load — defines constants, calls WC()',
    'WC() → WooCommerce::instance() constructs the singleton: define_constants(), define_tables(), includes(), init_hooks()',
    'init_hooks() registers callbacks, including add_action( \'init\', [ $this, \'init\' ], 0 )',
    'On plugins_loaded (priority -1): on_plugins_loaded() fires the woocommerce_loaded action',
    'On WordPress init (priority 0): WooCommerce::init() runs — fires before_woocommerce_init, loads text domain, builds factories, registers post types / taxonomies / session / cart, then fires woocommerce_init',
    'On rest_api_init: REST and Store API routes register',
    'The request proceeds as a normal WordPress request, now WooCommerce-aware',
  ]}
  caption="WooCommerce bootstrap. Your integration code normally waits until at least before_woocommerce_init (for feature flags) or woocommerce_init (for everything else)."
/>

WooCommerce fires its own actions during this sequence so extensions can hook
the right moment:

| Hook | Fires | Use it for |
| --- | --- | --- |
| `woocommerce_loaded` | On WordPress `plugins_loaded`, priority `-1` — after every plugin is loaded, before WordPress `init` | Code that needs WooCommerce's classes/functions to exist but must run before `init` |
| `before_woocommerce_init` | At the start of `WooCommerce::init()` (on WordPress `init`, priority 0) | Declaring feature compatibility — HPOS, Cart/Checkout Blocks |
| `woocommerce_init` | At the end of `WooCommerce::init()`, same tick | Most integration setup — factories, post types, and the session now exist |
| `init` (WordPress, priority > 0) | After `WooCommerce::init()` has run | Anything depending on the `product` post type or WooCommerce taxonomies |

<SafetyLevel level="recommended">
  Declare feature compatibility from a callback on
  <code>before_woocommerce_init</code>:

  ```php
  // Main plugin file. Runs during WordPress init.
  add_action( 'before_woocommerce_init', function () {
    if ( class_exists( \Automattic\WooCommerce\Utilities\FeaturesUtil::class ) ) {
      \Automattic\WooCommerce\Utilities\FeaturesUtil::declare_compatibility( 'custom_order_tables', __FILE__, true );
      \Automattic\WooCommerce\Utilities\FeaturesUtil::declare_compatibility( 'cart_checkout_blocks', __FILE__, true );
    }
  } );
  ```

  The feature slugs are <code>custom_order_tables</code> (HPOS) and
  <code>cart_checkout_blocks</code>. Declaring later has no effect — the plugin
  shows as "incompatible" and blocks the merchant from enabling the feature.
</SafetyLevel>

## The `WC()` singleton

`WC()` is a global accessor that returns the one WooCommerce instance. It is
the entry point to the main runtime objects:

| Accessor | Is | Notes |
| --- | --- | --- |
| `WC()->cart` (property) | `WC_Cart` | The visitor's cart. Loaded on the front end; `null` on admin / most REST / cron unless `wc_load_cart()` is called |
| `WC()->session` (property) | `WC_Session_Handler` | Per-visitor key/value store backing the cart, coupons, chosen shipping |
| `WC()->customer` (property) | `WC_Customer` | Current customer — address, tax location, logged-in or guest |
| `WC()->query` (property) | `WC_Query` | Front-end query manipulation for shop / product pages |
| `WC()->product_factory` / `WC()->order_factory` (property) | factories | Build `WC_Product` / `WC_Order` objects of the right subclass |
| `WC()->countries` (property) | `WC_Countries` | Country / state lists, address formats, tax base location |
| `WC()->checkout()` (method) | `WC_Checkout` | Checkout controller — field definitions, validation, order creation |
| `WC()->mailer()` (method) | `WC_Emails` | The transactional email system |
| `WC()->payment_gateways()` (method) | `WC_Payment_Gateways` | Registry of payment gateways |
| `WC()->shipping()` (method) | `WC_Shipping` | Shipping method / zone registry and package calculation |
| `WC()->queue()` (method) | Action Scheduler proxy | Schedule background jobs |

<Callout type="warn">
  `WC()->cart` and `WC()->session` are **context-sensitive**. On admin, cron,
  and many REST requests they are `null` or empty because there is no visitor
  session — `WooCommerce::init()` only calls `initialize_cart()` on front-end
  requests. Code that assumes a cart always exists breaks when it runs in the
  wrong context.
</Callout>

## The data layer: CRUD classes and data stores

Since WooCommerce 3.0, stored entities are accessed through a two-part
pattern that deliberately hides *where* the data physically lives:

<LayerStack
  layers={[
    { name: 'CRUD class', note: 'WC_Product (extends WC_Abstract_Legacy_Product → WC_Data), WC_Order (extends WC_Abstract_Order → WC_Data), WC_Customer, WC_Coupon — an in-memory object with typed getters/setters and a save() method. This is the API you use.' },
    { name: 'Data store', note: 'WC_Data_Store::load( \'product\' | \'order\' | \'customer\' | \'coupon\' ) returns a store class — e.g. WC_Product_Data_Store_CPT, or for orders WC_Order_Data_Store_CPT (legacy) vs OrdersTableDataStore (HPOS). Swappable via the woocommerce_data_stores and woocommerce_<type>_data_store filters.' },
    { name: 'Storage', note: 'wp_posts + wp_postmeta, the wc_product_meta_lookup table, or the dedicated wc_order* tables — an implementation detail the CRUD class shields you from.' },
  ]}
  caption="Why $order->get_total() is the right call and get_post_meta( $id, '_order_total' ) is not: the data store, not your code, decides where the value comes from."
/>

The practical rules:

<SafetyLevel level="recommended">
  Read and write WooCommerce entities through their CRUD class:
  <code>wc_get_product( $id )</code>, <code>wc_get_order( $id )</code>,
  <code>new WC_Customer( $id )</code>. Call <code>-&gt;save()</code> once after
  setting values. This stays correct across HPOS and future storage changes.
</SafetyLevel>

<SafetyLevel level="dangerous">
  Writing directly to <code>wp_postmeta</code> for orders, or assuming a
  specific table layout. Under HPOS the write goes to the wrong place or is
  silently ignored, and reports/emails then disagree with the database.
</SafetyLevel>

## Sessions

For anything that must persist across requests but is not a user account —
the guest cart, applied coupons, chosen shipping method, checkout progress —
WooCommerce uses its own **session**, separate from PHP sessions.

<Lifecycle
  steps={[
    'First front-end action that needs a session (e.g. add to cart) creates one via WC_Session_Handler',
    'A cookie named wp_woocommerce_session_<COOKIEHASH> is set (name filterable via woocommerce_cookie)',
    'Session data is written to the wp_woocommerce_sessions table, keyed by the customer/session ID in that cookie',
    'On later requests the cookie identifies the row; WC()->session loads it',
    'For logged-in users the session key is the user ID',
    'Expired rows are purged on the woocommerce_cleanup_sessions daily cron event',
  ]}
  caption="The WooCommerce session lifecycle — the backbone of the cart for guests."
/>

<VersionNote version="WooCommerce 11.0.1">
  11.0.1 moved guest session cookies to a stronger, salted hashing scheme
  (with backward compatibility for existing cookies). The table name and the
  `woocommerce_cleanup_sessions` schedule are unchanged.
</VersionNote>

<Callout type="info">
  Full-page caching and sessions interact badly if misconfigured: a cached
  page can show one visitor's cart count to another. Hosts and caching plugins
  normally exclude cart/checkout/account pages and vary on the session cookie.
  This gets a full treatment in the Performance section *(planned)*.
</Callout>

## Classic and Blocks are two front-ends on one core

A recurring architectural fact: the **data and business logic layer is
shared**, but the storefront presentation exists in two implementations.

<ClassicVsBlocks
  classic="Shortcodes and PHP templates render cart/checkout. Server-rendered, driven by admin-ajax and classic template hooks. The path most existing code targets."
  blocks="React components render cart/checkout, talking to the Store API. Customized through block settings, Slot/Fill, and integration interfaces — not PHP template hooks."
/>

Both ultimately call the same `WC()->cart`, the same totals calculation, and
the same order-creation code. The split is at the edge, not the core — which
is why "change the value in core logic, change the presentation per
front-end" is the reliable customization strategy.

<VersionNote version="WooCommerce 11.0.1">
  Since WooCommerce 8.3 the **Cart, Checkout, and Order Confirmation Blocks are
  the default** on new installs. Stores created before 8.3 keep the classic
  shortcode pages until a merchant migrates them (WooCommerce → Status → Tools).
  So a given store can be on either front-end — never assume.
</VersionNote>
