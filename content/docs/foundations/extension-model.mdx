<PageMeta priority="P0" audience="Intermediate → Advanced" />

WooCommerce is built to be changed without editing it. There are four
mechanisms for that, and they are not alternatives to pick from at random —
each operates at a different layer, and real customizations often use two or
three together. This page is the map of the system; the Development section
*(planned)* documents each mechanism in depth.

## The four mechanisms

<LayerStack
  layers={[
    { name: 'Actions (hooks)', note: 'Run code at a named moment. Add markup, trigger side effects, register things. Cannot change a value that has already been computed.' },
    { name: 'Filters', note: 'Transform a value as it passes a named point. Change a price, a label, an array of fields, a query. Must return the value.' },
    { name: 'Template overrides', note: 'Replace a classic PHP template file with your own copy in the theme. Full control of markup for that fragment; you now own the copy.' },
    { name: 'Blocks (Cart/Checkout Blocks)', note: 'Extend the React storefront via block settings, Slot/Fill, and integration interfaces backed by the Store API.' },
  ]}
  caption="Ordered roughly from safest / most surgical to most invasive / most powerful."
/>

## Actions — change *what happens*

An action is a point in execution where WooCommerce calls
`do_action( 'some_hook', $context… )`. Your callback runs there for effect;
its return value is discarded.

- **Good for:** outputting extra markup at a known position, sending a
  notification, writing a log row, creating related data when an order
  completes, enqueueing a script on WooCommerce pages.
- **Cannot:** change a value WooCommerce already calculated. If the price is
  wrong, an action fired after pricing cannot fix it.

<VerifyNote>representative core action names for storefront positions (e.g. around the add-to-cart button, checkout fields, order-received) in 11.0.1</VerifyNote>

## Filters — change *a value*

A filter is `apply_filters( 'some_filter', $value, $context… )`. Your callback
receives `$value`, returns a (possibly modified) version, and WooCommerce uses
what you return.

- **Good for:** adjusting a price, relabelling a button, adding/removing
  checkout fields, altering a product query, changing an email recipient,
  toggling whether a gateway is available.
- **Must:** always return a value — returning nothing sets it to `null` and
  breaks everything downstream.

<SafetyLevel level="recommended">
  For a value change, a filter is almost always the correct mechanism and the
  highest-safety one. It survives updates and touches nothing else.
</SafetyLevel>

<VerifyNote>representative core filter names for common value changes (catalog price, cart item price, checkout fields, gateway availability) in 11.0.1</VerifyNote>

### Actions vs filters — the test

<DecisionGuide>
  <Choice when="you want something to appear or happen">
    Action. Hook the position, echo or do your thing.
  </Choice>
  <Choice when="you want an existing value to be different">
    Filter. Hook the value, return the new one.
  </Choice>
  <Choice when="your action echoes markup to 'fix' a wrong number">
    Stop — you are patching a symptom. Find the filter on the value.
  </Choice>
</DecisionGuide>

## Template overrides — change *classic markup*

WooCommerce renders classic storefront fragments from PHP files in its
`templates/` directory, loaded through a resolver that checks your **theme**
first. Copy a template to `your-theme/woocommerce/<same-path>` and your copy
wins.

<Lifecycle
  steps={[
    'WooCommerce calls its template loader for e.g. cart/cart-totals.php',
    'The loader looks in your child theme, then parent theme, then WooCommerce',
    'First match wins — your themed copy is used if present',
    'The template runs with a defined set of variables in scope',
    'Action hooks inside the template still fire — from your copy too, if you keep them',
  ]}
  caption="The classic template override mechanism. It is a theme feature, resolved at render time."
/>

<SafetyLevel level="risky">
  A template override is a **maintained fork of one file**. When WooCommerce
  changes that template in an update, your copy does not get the change — and
  can silently drop new markup, hooks, or accessibility fixes. WooCommerce's
  system report flags overridden templates that are out of date. Use only when
  no hook or filter reaches what you need.
</SafetyLevel>

<VerifyNote>the template resolver function names (`wc_get_template`, `wc_locate_template`?), the theme sub-directory (`woocommerce/`), and the outdated-template version-check mechanism for 11.0.1</VerifyNote>

<Callout type="warn">
  Template overrides only affect the **classic** front-end. They do nothing to
  the Cart and Checkout **Blocks** — a template override of `checkout/*.php`
  has no effect on a store using the Checkout Block.
</Callout>

## Blocks — change *the React storefront*

The Cart and Checkout Blocks render on the client and get their data from the
[Store API](/docs/foundations/wordpress-fundamentals#the-rest-api). They are
not extended with PHP template hooks. Instead:

/>

<VerifyNote>the current Blocks extensibility API names — Slot/Fill region names, the checkout integration registration function, and the Store API extend mechanism (`ExtendSchema` / `woocommerce_store_api_register_endpoint_data`?) for 11.0.1</VerifyNote>

## How they compose

Real customizations layer the mechanisms. A worked shape — adding a gift-wrap
option to checkout:

    'Filter: add a fee to the cart totals when the option is set',
    'Action: on order creation, save the choice as order meta',

## Choosing a mechanism

<DecisionGuide>
  <Choice when="a filter exists for the value you want to change">
    Use it. Done. Highest safety, zero maintenance.
  </Choice>
  <Choice when="you need to add output at a known position">
    Use the action at that position.
  </Choice>
  <Choice when="no hook reaches the markup and the store is classic">
    Override the template. Record it; re-check on every WooCommerce update.
  </Choice>
  <Choice when="the store uses Cart/Checkout Blocks">
    Use block settings, then Slot/Fill, then the integration interface. Do not
    reach for PHP template overrides.
  </Choice>
  <Choice when="only editing a core file would work">
    Stop. Re-scope the requirement, request an upstream hook, or build a proper
    extension around the constraint.
  </Choice>
</DecisionGuide>
