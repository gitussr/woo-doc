<PageMeta priority="P0" audience="Intermediate → Advanced" />

WooCommerce is built to be changed without editing it. There are four
mechanisms for that, and they are not alternatives to pick from at random —
each operates at a different layer, and real customizations often use two or
three together. This page is the map of the system; the Development section
*(planned)* documents each mechanism in depth.

## The four mechanisms

<LayerStack
  layers={[
    { name: 'Actions (hooks)', note: 'Run code at a named moment. Add markup, trigger side effects, register things. Cannot change a value that has already been computed.' },
    { name: 'Filters', note: 'Transform a value as it passes a named point. Change a price, a label, an array of fields, a query. Must return the value.' },
    { name: 'Template overrides', note: 'Replace a classic PHP template file with your own copy in the theme. Full control of markup for that fragment; you now own the copy.' },
    { name: 'Blocks (Cart/Checkout Blocks)', note: 'Extend the React storefront via block settings, Slot/Fill, and integration interfaces backed by the Store API.' },
  ]}
  caption="Ordered roughly from safest / most surgical to most invasive / most powerful."
/>

## Actions — change *what happens*

An action is a point in execution where WooCommerce calls
`do_action( 'some_hook', $context… )`. Your callback runs there for effect;
its return value is discarded.

- **Good for:** outputting extra markup at a known position, sending a
  notification, writing a log row, creating related data when an order
  completes, enqueueing a script on WooCommerce pages.
- **Cannot:** change a value WooCommerce already calculated. If the price is
  wrong, an action fired after pricing cannot fix it.

Representative core actions (all still present in 11.0.1):

| Action | Position |
| --- | --- |
| `woocommerce_before_add_to_cart_form` / `woocommerce_after_add_to_cart_button` | Around the single-product add-to-cart form |
| `woocommerce_single_product_summary` | The product summary column (priced callbacks at set priorities: title 5, price 10, add-to-cart 30) |
| `woocommerce_checkout_before_customer_details` / `woocommerce_review_order_before_payment` | Classic checkout regions |
| `woocommerce_checkout_create_order` | Just before a new order is saved — set order data here |
| `woocommerce_thankyou` | The order-received page, with the order ID |
| `woocommerce_order_status_changed` | Any order status transition |

## Filters — change *a value*

A filter is `apply_filters( 'some_filter', $value, $context… )`. Your callback
receives `$value`, returns a (possibly modified) version, and WooCommerce uses
what you return.

- **Good for:** adjusting a price, relabelling a button, adding/removing
  checkout fields, altering a product query, changing an email recipient,
  toggling whether a gateway is available.
- **Must:** always return a value — returning nothing sets it to `null` and
  breaks everything downstream.

<SafetyLevel level="recommended">
  For a value change, a filter is almost always the correct mechanism and the
  highest-safety one. It survives updates and touches nothing else.
</SafetyLevel>

Representative core filters (all still present in 11.0.1):

| Filter | Changes |
| --- | --- |
| `woocommerce_product_get_price` / `woocommerce_product_get_regular_price` / `woocommerce_product_get_sale_price` | The stored price a `WC_Product` returns |
| `woocommerce_get_price_html` | The formatted price HTML shown in the catalog |
| `woocommerce_cart_item_price` / `woocommerce_cart_item_subtotal` | The *displayed* per-line price in the cart (not the amount charged — that is set via `set_price()` on `woocommerce_before_calculate_totals`) |
| `woocommerce_checkout_fields` | The classic checkout field definitions |
| `woocommerce_available_payment_gateways` | Which gateways are offered at checkout |
| `woocommerce_email_recipient_<id>` | The recipient of a given transactional email |

### Actions vs filters — the test

<DecisionGuide>
  <Choice when="you want something to appear or happen">
    Action. Hook the position, echo or do your thing.
  </Choice>
  <Choice when="you want an existing value to be different">
    Filter. Hook the value, return the new one.
  </Choice>
  <Choice when="your action echoes markup to 'fix' a wrong number">
    Stop — you are patching a symptom. Find the filter on the value.
  </Choice>
</DecisionGuide>

## Template overrides — change *classic markup*

WooCommerce renders classic storefront fragments from PHP files in its
`plugins/woocommerce/templates/` directory. Core loads them with
`wc_get_template()` / `wc_get_template_part()`, which call `wc_locate_template()`
to resolve the path — checking `yourtheme/woocommerce/<same-path>` first, then
falling back to the plugin. Copy a template into that theme folder (minus the
`templates/` segment) and your copy wins. The resolution can also be filtered
via `woocommerce_locate_template` or `wc_get_template`.

<Lifecycle
  steps={[
    'Core calls wc_get_template( \'cart/cart-totals.php\' )',
    'wc_locate_template() checks child theme → parent theme → WooCommerce plugin',
    'First match wins — your themed copy is used if present',
    'The template runs with a defined set of $args in scope',
    'Action hooks inside the template still fire — from your copy too, if you keep them',
  ]}
  caption="The classic template override mechanism. It is a theme feature, resolved at render time."
/>

<SafetyLevel level="risky">
  A template override is a **maintained fork of one file**. Each core template
  carries an <code>@version</code> docblock; WooCommerce → Status → System
  Status lists every overridden template whose <code>@version</code> is behind
  the current core template ("version X is out of date. The core version is
  Y"). When WooCommerce changes that template, your copy does not get the
  change and can silently drop new markup, hooks, or accessibility fixes. Use
  only when no hook or filter reaches what you need.
</SafetyLevel>

<Callout type="warn">
  Template overrides only affect the **classic** front-end. They do nothing to
  the Cart and Checkout **Blocks** — a template override of `checkout/*.php`
  has no effect on a store using the Checkout Block.
</Callout>

## Blocks — change *the React storefront*

The Cart and Checkout Blocks render on the client and get their data from the
[Store API](/docs/foundations/wordpress-fundamentals#the-rest-api). They are
not extended with PHP template hooks. Instead:

<LayerStack
  layers={[
    { name: 'Block settings', note: 'Editor-side attributes on each block — the no-code surface.' },
    { name: 'Slot / Fill', note: 'React fills like ExperimentalOrderMeta, ExperimentalOrderShippingPackages, ExperimentalDiscountsMeta — rendered via registerPlugin() with scope "woocommerce-checkout"' },
    { name: 'Checkout filters', note: 'registerCheckoutFilters() from @woocommerce/blocks-checkout — transform labels, item names, totals strings client-side' },
    { name: 'IntegrationInterface (PHP)', note: 'register scripts/styles/data with the blocks via the woocommerce_blocks_checkout_block_registration / _cart_block_registration actions' },
    { name: 'Store API extension (PHP)', note: 'ExtendSchema, via woocommerce_store_api_register_endpoint_data() to add namespaced data to cart/checkout responses and woocommerce_store_api_register_update_callback() to receive data back' },
  ]}
  caption="The Blocks extension surface. Conceptually parallel to hooks + templates, but implemented in JS + a data API."
/>

<ClassicVsBlocks
  classic="Customize with actions, filters, and template overrides. Mature, heavily documented, most tutorials target it."
  blocks="Customize with block settings, Slot/Fill, checkout filters, IntegrationInterface, and Store API data. Classic display and process hooks — woocommerce_checkout_fields, woocommerce_review_order_before_payment, woocommerce_checkout_order_processed and the like — do NOT run; the server-side equivalent is woocommerce_store_api_checkout_order_processed and friends."
/>

## How they compose

Real customizations layer the mechanisms. A worked shape — adding a gift-wrap
option to checkout:

  steps={[
    'Filter: add a "gift wrap" field to the checkout field list (classic) / render it in a Slot (Blocks)',
    'Filter: add a fee to the cart totals when the option is set',
    'Action: on order creation, save the choice as order meta',
    'Action: in the admin order screen and the customer email, display the saved choice',
    'Template override or Blocks Slot: only if the fee row needs custom presentation a filter cannot give',
  ]}

/>

## Choosing a mechanism

<DecisionGuide>
  <Choice when="a filter exists for the value you want to change">
    Use it. Done. Highest safety, zero maintenance.
  </Choice>
  <Choice when="you need to add output at a known position">
    Use the action at that position.
  </Choice>
  <Choice when="no hook reaches the markup and the store is classic">
    Override the template. Record it; re-check on every WooCommerce update.
  </Choice>
  <Choice when="the store uses Cart/Checkout Blocks">
    Use block settings, then Slot/Fill, then the integration interface. Do not
    reach for PHP template overrides.
  </Choice>
  <Choice when="only editing a core file would work">
    Stop. Re-scope the requirement, request an upstream hook, or build a proper
    extension around the constraint.
  </Choice>
</DecisionGuide>
