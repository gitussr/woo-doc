WooCommerce is a WordPress plugin. Every capability it has is either a
WordPress mechanism it reuses or a mechanism it adds *in the shape WordPress
expects*. If you understand these seven WordPress subsystems, most of
WooCommerce's structure stops being surprising.

This page is a WooCommerce-oriented refresher, not a full WordPress course.
Each section says what the mechanism is, then **how WooCommerce leans on it**.

## The request lifecycle

Every front-end WooCommerce page is a normal WordPress request. Nothing about
a cart or a checkout changes the boot sequence — WooCommerce just registers
callbacks at specific points in it.

<VersionNote version="WordPress 7.1 · WooCommerce 11.0.1">
  These WordPress action names (`plugins_loaded`, `setup_theme`,
  `after_setup_theme`, `init`, `wp_loaded`, `parse_request`, `wp`,
  `template_redirect`) are long-standing core API and fire in this order on a
  normal front-end request. WooCommerce's own `init()` method is hooked to
  WordPress `init` at priority `0`; the exact internal sequence is in
  [WooCommerce Architecture](/docs/foundations/woocommerce-architecture#bootstrap-from-plugin-file-to-wc).
</VersionNote>

## Post types

WordPress stores most editable content as rows in one table (`wp_posts`),
distinguished by a `post_type` column. `post` and `page` are built in;
plugins register their own with `register_post_type()`.

WooCommerce registers several custom post types:

| Post type | Represents | Notes |
| --- | --- | --- |
| `product` | A catalog product | `public`, has archives, uses custom taxonomies |
| `product_variation` | One variation of a variable product | Child of a `product`; not `public`, hidden from the admin list |
| `shop_coupon` | A coupon | Not `public`; admin-only |
| `shop_order` | An order | Registered for compatibility; **not** the storage under HPOS (see below) |
| `shop_order_refund` | A refund against an order | Child of an order |
| `shop_webhook` | A REST API webhook subscription | Internal |

WooCommerce also registers taxonomies attached to `product`: `product_cat`
and `product_tag` (the visible catalog taxonomies), `product_type` and
`product_visibility` (internal, `public => false`, `hierarchical => false`),
and one taxonomy per global attribute, named `pa_<attribute>` (e.g.
`pa_color`).

<Callout type="warn">
  **Orders are the exception.** With High-Performance Order Storage (HPOS)
  enabled, orders and refunds are stored in dedicated tables, not as
  `shop_order` posts. Treating an order as "just a post" is the single most
  common outdated assumption in older WooCommerce tutorials. See the HPOS
  section *(planned)* and
  [WooCommerce Data Model](/docs/foundations/woocommerce-data-model).
</Callout>

## Metadata

Alongside each post, WordPress keeps arbitrary key/value pairs in
`wp_postmeta` (`post_id`, `meta_key`, `meta_value`), read with
`get_post_meta()`. It is schemaless and flexible, and expensive to query at
scale because `meta_value` is a long text column with no useful index.

How WooCommerce uses it:

- **Product data** — almost every product field is post meta under an
  underscore-prefixed key: `_regular_price`, `_sale_price`, `_price`, `_sku`,
  `_stock`, `_stock_status`, `_weight`, `_length` / `_width` / `_height`,
  `_tax_class`, `_manage_stock`, `_downloadable`, `_virtual`, and more.
- **Lookup tables** — because meta queries are slow, WooCommerce maintains
  `wp_wc_product_meta_lookup` (added in WooCommerce 3.7): one row per product
  with real columns for `sku`, `min_price` / `max_price`, `stock_status`,
  `stock_quantity`, `onsale`, `rating_count`, `average_rating`, `total_sales`,
  `virtual`, `downloadable`, `tax_status`, `tax_class`. Catalog queries and
  sorting hit this table instead of `wp_postmeta`, and WooCommerce keeps it in
  sync on save.
- **CRUD abstraction** — you are encouraged to read product and order data
  through `WC_Product` / `WC_Order` getter methods, not `get_post_meta()`
  directly, so that HPOS and lookup tables stay correct. This is covered in
  [WooCommerce Data Model](/docs/foundations/woocommerce-data-model).

<SafetyLevel level="risky">
  Reading WooCommerce data with <code>get_post_meta()</code> works today for
  products but bypasses the data-store layer. For orders under HPOS it can
  return stale data or nothing. Prefer the CRUD getters.
</SafetyLevel>

## Options

`wp_options` holds site-wide settings as key/value rows, read with
`get_option()`. Rows flagged `autoload = yes` are **all loaded on every
request** into memory. A bloated autoload set is a classic WordPress
performance problem.

WooCommerce uses options for essentially all store configuration — pages,
currency, tax behavior, checkout options, email settings, gateway settings —
mostly under a `woocommerce_` key prefix (for example `woocommerce_currency`,
`woocommerce_cart_page_id`, `woocommerce_calc_taxes`,
`woocommerce_default_country`). Many are autoloaded; the store's own settings
plus each active extension's settings all add to the per-request autoload
payload.

<Callout type="info">
  When the Performance section *(planned)* is written, autoloaded option
  weight from WooCommerce and its extensions gets its own treatment —
  it is one of the highest-leverage things to audit on a slow store.
</Callout>

## Hooks: actions and filters

The hook system is how WordPress code is changed without editing it. Two
kinds:

<LayerStack
  layers={[
    { name: 'Action', note: 'a named moment — "do something now". Callbacks run for side effects; return values are ignored. add_action() / do_action().' },
    { name: 'Filter', note: 'a named value passing through — "transform this and return it". The callback must return a value. add_filter() / apply_filters().' },
  ]}
/>

Both share the same mechanics: callbacks register with a **priority** (lower
runs earlier, default 10) and a declared number of **accepted arguments**.
WooCommerce exposes hundreds of each. The distinction matters:

- Want to *add markup* next to the price? An **action** at that position.
- Want to *change the price value*? A **filter** on the value.

Putting display logic in a value filter, or trying to change a value from an
action, is a frequent source of "my code runs but nothing changes".

<VersionNote version="WooCommerce 11.0.1">
  Hook *names* are the most version-sensitive API surface in WooCommerce.
  Specific hooks named across the Foundations pages have been checked against
  WooCommerce 11.0.1; anything still unverified carries a <VerifyNote /> tag.
  The Development section *(planned)* documents hook discovery and debugging in
  depth.
</VersionNote>

## Cron and scheduled work

WordPress has "cron" (`wp_schedule_event()`, the `wp_cron` option) that runs
due tasks on regular page loads — not a real system cron unless wired to one.
It is fine for light, non-urgent work and unreliable for anything precise or
high-volume.

WooCommerce bundles **Action Scheduler**, a more robust queue built on top of
WordPress. Since Action Scheduler 3.0 it stores jobs in its own tables —
`wp_actionscheduler_actions`, `wp_actionscheduler_logs`,
`wp_actionscheduler_groups`, `wp_actionscheduler_claims` — processes them in
batches on the `action_scheduler_run_queue` hook (dispatched roughly once a
minute via WP-Cron), and retries failures. WooCommerce and many extensions
use it for deferred emails, webhook delivery, analytics/report generation,
and data migrations including the HPOS backfill.

<VersionNote version="WooCommerce 11.0 · Action Scheduler 4.0">
  Two behaviour changes to know if you schedule your own jobs: unique-action
  checks now include the action's **arguments** (previously hook + group only),
  so more actions can be created than before; and failed actions are now
  auto-purged after ~3 months (`action_scheduler_retention_period_for_failed`,
  disable via `action_scheduler_enable_failed_action_cleanup`).
</VersionNote>

<SafetyLevel level="recommended">
  For your own deferred work in a WooCommerce context, schedule it through
  Action Scheduler rather than raw <code>wp_schedule_single_event()</code> —
  you get batching, retries, and an admin view of the queue.
</SafetyLevel>

## The REST API

WordPress ships a REST API under `/wp-json/`. WooCommerce adds two distinct
API surfaces on top:

| API | Base route | Purpose | Auth |
| --- | --- | --- | --- |
| WooCommerce REST API | `/wp-json/wc/v3/` | Server-to-server: `products`, `orders`, `customers`, `coupons`, `products/reviews`, `reports`, `system_status`, settings, webhooks | API keys (consumer key/secret) or cookie auth + nonce |
| Store API | `/wp-json/wc/store/v1/` | Front-end: `cart`, `cart/items`, `cart/coupons`, `checkout`, `products`, `products/collection-data` — drives the Cart/Checkout Blocks and headless | Cart token / nonce; designed for the browser, no API keys |

The two are not interchangeable. `wc/v3` is an admin/integration tool with
full CRUD on stored records. The Store API is a customer-facing surface that
manages a *session cart* and drives the Cart and Checkout Blocks; it is
versioned separately (`v1`) and is not a drop-in for `wc/v3`. Both get their
own pages in later phases (Development section, *planned*).
