<PageMeta priority="P1" audience="Intermediate → Advanced" />

High-Performance Order Storage replaces "an order is a post" with "an order
is rows in tables shaped for orders." It has been the default for **new**
WooCommerce installs since version 8.2; stores created earlier keep legacy
storage until a merchant migrates. Either way, the `WC_Order` API is
identical — this page is about what changes underneath it, and what a
plugin author must do to stay correct across both.

## Why HPOS exists

<SafetyLevel level="risky" title="What legacy storage cost">
  An order as a `shop_order` post meant every field — status, totals,
  addresses, payment details — was a separate row in `wp_postmeta`, an
  unindexed-by-value table shared with every other post type on the site.
  High-volume stores felt this as slow order queries, lock contention during
  checkout, and a `wp_postmeta` table that dwarfed everything else in the
  database.
</SafetyLevel>

HPOS gives orders their own tables with real, indexed columns — the same
"stop abusing postmeta" move the
[product meta lookup table](/docs/data-storage/database#why-the-lookup-tables-exist)
made for products years earlier, applied to the entire order record.

## The four tables

<LayerStack
  layers={[
    { name: 'wc_orders', note: 'the order record: id, status, type, currency, tax_amount, total_amount, customer_id, billing_email, date_created_gmt, date_updated_gmt, parent_order_id (for refunds), payment_method(+title), ip_address, transaction_id, user_agent, customer_note' },
    { name: 'wc_order_addresses', note: 'one row per address_type ("billing" / "shipping") per order: name, company, address lines, city, state, postcode, country, email, phone' },
    { name: 'wc_order_operational_data', note: 'internal state: created_via, order_key, prices_include_tax, order_stock_reduced, download_permission_granted, cart_hash, date_paid_gmt, date_completed_gmt, shipping/discount tax + total amounts, recorded_sales' },
    { name: 'wc_orders_meta', note: 'a postmeta-shaped escape hatch (order_id, meta_key, meta_value) for anything not promoted to a real column — extensions\' custom data' },
  ]}
  caption="Four tables replace one post + its meta rows. Order items keep their own tables, untouched by HPOS."
/>

<Callout type="info">
  `woocommerce_order_items` and `woocommerce_order_itemmeta` (the line items,
  shipping, fees, coupons, tax) are **not part of HPOS** — they had their own
  dedicated tables long before HPOS existed, and HPOS did not need to touch
  them. Only the order *record* moved.
</Callout>

## Three storage modes

<Lifecycle
  steps={[
    'High-performance order storage — wc_orders* tables are authoritative; wp_posts is not written',
    'WordPress post tables (legacy) — wp_posts/wp_postmeta are authoritative; wc_orders* is not written',
    'WordPress post tables + "Enable compatibility mode" — wp_posts remains authoritative but every write is synced to wc_orders* as well',
  ]}
  caption="Set at WooCommerce → Settings → Advanced → Features. Compatibility mode is the safe path for switching modes without a hard cutover."
/>

Compatibility mode exists so a store — and every plugin it runs — can be
verified against both storages before HPOS becomes authoritative. It costs a
write penalty (every order write happens twice) in exchange for a safe
rollback.

## Migration

Switching an existing store from legacy to HPOS is a background job, not a
flag flip:

<Lifecycle
  steps={[
    'Compatibility mode is turned on — new orders start writing to both storages',
    'A background migration (Action Scheduler-driven, batched) backfills existing orders from wp_posts into wc_orders*',
    'Merchant verifies the store behaves correctly with both storages populated',
    'Authoritative storage is switched to "High-performance order storage"',
    'wp_posts rows can optionally be kept in sync going forward, or migration is considered complete',
  ]}
  caption="Migration runs in the background in batches — it is designed not to lock a live store with a large order history."
/>

<VerifyNote>confirm the exact migration controller class/CLI command and whether legacy post rows are deleted or retained by default after migration completes in 11.0.1</VerifyNote>

<SafetyLevel level="recommended">
  On a store with a non-trivial order history, run the migration during low
  traffic and watch **WooCommerce → Status → Scheduled Actions** for the
  batch jobs — do not force it to complete synchronously.
</SafetyLevel>

## Writing code that works in both modes

<DecisionGuide>
  <Choice when="reading or writing an order">
    `wc_get_order( $id )` / `wc_get_orders( $args )` and the `WC_Order`
    getters/setters. This is storage-agnostic by design — the same call works
    whichever mode is authoritative.
  </Choice>
  <Choice when="querying orders in bulk (a report, an export)">
    `wc_get_orders()` with its query args, not `WP_Query` and not a
    hand-written join against `wp_posts`. Under HPOS, `WP_Query` for orders
    returns nothing.
  </Choice>
  <Choice when="you must run raw SQL for something CRUD cannot express">
    Detect the active mode first
    (`Automattic\WooCommerce\Utilities\OrderUtil::custom_orders_table_usage_is_enabled()`)
    and branch — query `wc_orders` or `wp_posts` accordingly. Treat this as a
    last resort, and re-check it against every WooCommerce update.
  </Choice>
  <Choice when="you are shipping a plugin that touches orders at all">
    Declare compatibility explicitly — see
    [Architecture → bootstrap](/docs/foundations/woocommerce-architecture#bootstrap-from-plugin-file-to-wc):
    `FeaturesUtil::declare_compatibility( 'custom_order_tables', __FILE__, true )`
    on `before_woocommerce_init`, after auditing for direct table/postmeta
    access.
  </Choice>
</DecisionGuide>

<SafetyLevel level="dangerous">
  Reading or writing order data with `get_post_meta()` / `update_post_meta()`,
  or querying `wp_posts` for `shop_order`. Under HPOS this silently reads
  stale data or writes to a table nothing else looks at — the failure mode is
  data that is subtly wrong, not an error.
</SafetyLevel>

## What does not change

The `WC_Order`, `WC_Order_Item_*`, and `WC_Order_Refund` **APIs are
identical** in both modes — same getters, same setters, same hooks, same
[status-transition events](/docs/lifecycle/orders#the-transition-hook-family).
HPOS is a storage-layer change; it is not a new order lifecycle.
